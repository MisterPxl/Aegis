**Audit Aegis 0.2.0 — 7 septembre 2026**

**Corrections appliquées et vérifiées :** voir le [bilan des corrections](/Users/alexis.gomes/Projects/Aegis/Documentation~/Audit-2026-09-07/Fixes.md). L’analyse et les échecs ci-dessous décrivent la révision initiale, avant correction.

L’audit identifie **8 anomalies confirmées, dont 3 de priorité P1**. Les principaux risques sont le blocage de l’éditeur sur des références cycliques, la perte de règles enregistrées comme assets et l’échec de compilation d’un Player après import de l’exemple fourni. Ces défauts justifient une correction avant de considérer le package comme un contrôle fiable de livraison.

Révision examinée : `30e8db578e8bd4839f1566662363a674fc543ecf`. Revue du cœur, du dashboard, des règles, du CLI, du build gate, des exports, des manifestes, des samples et des deux extensions. Exécutions dans une copie temporaire du dépôt avec **Unity 6000.4.0f1**, sur macOS. Aucun correctif de production n’a été appliqué.

**Anomalies et corrections proposées**

1. **[P1] Le parcours des références cycliques ne termine pas.** [AegisRules.cs:226](/Users/alexis.gomes/Projects/Aegis/Editor/Rules/AegisRules.cs:226), également ligne 271 et dans la règle de références managées de Valkyrie.

   Les scanners appellent systématiquement `NextVisible(true)`. Un objet `[SerializeReference]` qui se référence lui-même fait revisiter indéfiniment les mêmes propriétés. Le reproducer s’arrête volontairement après 1 000 itérations ; le code de production ne possède pas cette limite. Comme `Evaluate` s’exécute sur le thread principal et que le budget de frame n’est vérifié qu’entre les règles, le bouton Cancel ne peut pas interrompre cette boucle. Le dashboard, le build gate et le CLI sont concernés. Mémoriser les `managedReferenceId` déjà visités et ne pas redescendre dans une référence déjà parcourue ; prévoir un parcours incrémental pour rendre l’annulation effective sur les scans longs.

2. **[P1] Les règles intégrées enregistrées comme assets ne se rechargent pas.** [AegisRules.cs:153](/Users/alexis.gomes/Projects/Aegis/Editor/Rules/AegisRules.cs:153).

   Les six classes concrètes `ScriptableObject` résident dans `AegisRules.cs`, sans fichier correspondant à leur nom. Pour `MissingMonoScriptRule`, `MonoScript.FromScriptableObject` renvoie `null`. Un asset créé puis sauvegardé contient `m_Script: {fileID: 0}` ; après déchargement et réimport, `LoadAssetAtPath<MissingMonoScriptRule>` renvoie `null`. Les fallbacks créés en mémoire masquent le problème, mais les règles configurées par l’utilisateur deviennent inutilisables. Placer chaque classe concrète dans son propre fichier portant son nom, avec un `.meta` stable, puis tester une sauvegarde suivie d’un réimport. Le même schéma de fichiers existe dans l’extension Valkyrie et dans l’exemple `SceneNamingRule` ; ces variantes n’ont pas été exécutées dans ce test.

3. **[P1] L’import du sample « Custom Rule » casse la compilation Player.** [AegisCustomRuleExample.cs:1](</Users/alexis.gomes/Projects/Aegis/Samples~/Custom Rule/AegisCustomRuleExample.cs:1>).

   Le sample est importé sous `Assets/Samples/.../Custom Rule/`, sans dossier `Editor`, sans assembly restreinte à l’éditeur et sans garde `UNITY_EDITOR`. Il dépend pourtant de `Aegis.Editor`. Après copie du sample à cet emplacement, une compilation des scripts Player pour macOS produit des erreurs `CS0246` sur `MisterPxl`, `AegisRuleAsset`, `AegisValidationContext` et `IAegisFindingSink`, avec zéro assembly produite. Déplacer le script dans `Editor/SceneNamingRule.cs` ou fournir une assembly Editor adaptée. La reproduction utilise l’API Unity de [compilation des scripts Player](https://docs.unity3d.com/cn/6000.0/ScriptReference/Build.Player.PlayerBuildInterface.CompilePlayerScripts.html) ; elle ne construit pas un Player complet.

4. **[P2] Les références cassées masquées dans l’inspecteur sont ignorées.** [AegisRules.cs:226](/Users/alexis.gomes/Projects/Aegis/Editor/Rules/AegisRules.cs:226).

   `NextVisible` limite la validation à la présentation de l’inspecteur. Le test crée deux champs sérialisés pointant vers le même GUID inexistant : le champ visible déclenche un finding, le champ `[HideInInspector]` n’en déclenche aucun. Une référence requise au runtime peut donc échapper au build gate. Parcourir toutes les propriétés sérialisées avec `Next`, en conservant la protection contre les cycles du point 1. La règle des entrées nulles utilise le même parcours et doit être traitée également.

5. **[P2] Les suppressions sont ignorées par le dashboard.** [AegisRunner.cs:233](/Users/alexis.gomes/Projects/Aegis/Editor/Runner/AegisRunner.cs:233), [AegisDashboardWindow.cs:314](/Users/alexis.gomes/Projects/Aegis/Editor/Dashboard/AegisDashboardWindow.cs:314).

   Le runner synchrone filtre les findings avec `IsSuppressed`, alors que `AegisInteractiveRun.Finish` sauvegarde la liste brute. Le bouton « Suppress Selected » enregistre l’exception puis appelle `RefreshFilter`, qui ne consulte pas non plus les suppressions. Le diagnostic reste donc affiché, compté et exporté après suppression, y compris après un nouveau Run interactif. Un test enregistrant une suppression avant l’exécution interactive reproduit ce comportement. Centraliser la finalisation du rapport et l’appliquer à tous les chemins d’exécution ainsi qu’au rafraîchissement après suppression.

6. **[P2] Le JUnit ne reflète pas le résultat effectif de validation.** [AegisReportWriters.cs:40](/Users/alexis.gomes/Projects/Aegis/Editor/Reports/AegisReportWriters.cs:40), également ligne 56.

   Les compteurs des règles sont établis avant les suppressions. Le writer les utilise directement et émet un `<failure>` même lorsque le rapport final ne contient plus aucun finding. Il traite également tout warning ou info comme un échec, indépendamment du seuil utilisé pour le code de sortie CLI. Enfin, une règle `Skipped` est exportée comme un testcase réussi, sans `<skipped>`. Les tests reproduisent le faux échec avec zéro finding actif et la perte du statut ignoré. Construire le JUnit depuis les findings effectifs, transmettre le seuil de blocage et représenter explicitement les règles ignorées et les erreurs d’exécution.

7. **[P2] Une sauvegarde précoce des réglages initialise mal les profils Build et CI.** [AegisSettings.cs:12](/Users/alexis.gomes/Projects/Aegis/Editor/Settings/AegisSettings.cs:12), [AegisSettings.cs:113](/Users/alexis.gomes/Projects/Aegis/Editor/Settings/AegisSettings.cs:113).

   Les profils sérialisés sont initialement nuls et ne sont configurés que par leurs getters. Sauvegarder les réglages avant d’avoir accédé aux profils laisse Unity matérialiser les champs inline avec les valeurs par défaut de `AegisValidationProfile`. `EnsureProfile` les accepte ensuite puisqu’ils ne sont plus nuls. Sur des réglages vierges, `AegisSettings.instance.Save()` suivi de `GetProfile` produit `Build=Interactive; CI=Interactive`, avec un budget de 8 ms au lieu de 1. L’ajout d’une suppression peut déclencher cette sauvegarde. Les rapports de build/CI portent alors le mauvais profil. Initialiser explicitement les trois profils avant toute sérialisation et prévoir une migration des réglages existants, sans écraser les filtres personnalisés.

8. **[P2] Une validation annulée remplace le dernier rapport par un succès incomplet.** [AegisRunner.cs:228](/Users/alexis.gomes/Projects/Aegis/Editor/Runner/AegisRunner.cs:228).

   `Finish` écrit systématiquement `last-report.json` et appelle `AegisRunResult.Succeed`, même après annulation. Le message d’annulation n’est pas exploité par le callback du dashboard, qui affiche simplement le résumé du rapport partiel. Le test `Start(); Cancel();` obtient effectivement `Success=true`. Une annulation avant les règles problématiques peut donc afficher zéro erreur et remplacer un rapport complet. Ajouter un état d’annulation persistant, l’afficher dans le dashboard et distinguer les rapports complets des rapports partiels dans le stockage et les exports.

**Portée et limites**

Le cœur ne déclare aucune dépendance UPM externe et son assembly est correctement limitée à l’éditeur. L’isolation des exceptions de règles, les fingerprints et les deux tests de conservation/parcours des scènes passent. Ces résultats ne couvrent pas la validité de toutes les règles sur de grands projets.

Les extensions Helios et Valkyrie ont été lues, mais leurs tests d’intégration/runtime n’ont pas été exécutés : elles ne figurent pas dans le manifeste du projet de validation fourni. L’installation Git avec résolution des dépendances des extensions, Unity 6000.0 annoncé comme minimum, les autres systèmes d’exploitation et un build Player complet restent hors des vérifications exécutées. Aucune conclusion d’absence de vulnérabilités de toutes les dépendances tierces n’est tirée de cet audit.
